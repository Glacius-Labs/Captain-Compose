# Pilot acceptance matrix

The acceptance runner targets a disposable Linux reference environment. It exercises
the released 1.0 agent state through an upgrade, then operates the new operator and
agent against an isolated Docker daemon and broker. Every result is tied to an
individual named check in the generated JSON report. A passing simulated restart is
not evidence of a physical host reboot or sudden power loss.

| Scenario | Runner evidence | Boundary |
| --- | --- | --- |
| 1.0 state upgrade with accepted work pending | Pending 1.0 inbox work is recovered by the upgraded agent and its result is observed | Requires a preserved 1.0 fixture generated by the 1.0 binary |
| Duplicate result query | Repeating a result query returns the same saved lifecycle event without another deployment mutation | Exercises application-level replay safety; MQTT QoS 1 may redeliver transport packets |
| Broker outage and event backlog independence | An accepted operation completes while result delivery is interrupted; reconnect recovers its saved result | At-least-once MQTT delivery can repeat packets; the runner does not claim exactly-once transport |
| Expiry and stale revision | An expired command and an expected-revision mismatch both fail without changing deployed state | Uses controlled expiry/revision values |
| Agent/process restart | Stop and restart the agent with the same state directory, then query the deployment | Does not simulate kernel restart or host power loss |
| State/data restore to a fresh agent | Restore a copied state directory and named data volume into a fresh isolated environment; query and verify data | Simulated fresh host; not a tested backup product or separate physical machine |
| State disk full | Run an isolated agent with a capped tmpfs state mount and observe bounded failure/recovery | Does not fill a host filesystem or Docker storage |
| Docker unavailable | Start or preflight the agent without a reachable disposable Docker daemon and verify a clear failure | The host Docker daemon and existing workloads remain outside the test |
| MQTT credential failure | Connect using an invalid isolated broker credential and verify startup failure | Test-only credentials |
| TLS certificate failure | Connect to the isolated TLS broker with a wrong CA/hostname and verify startup failure | Test certificates only |
| Physical reboot | Not run by this harness | Requires a separately approved disposable physical/virtual reference host |
| Sudden power loss | Not run by this harness | Requires controlled infrastructure capable of removing power safely |
| systemd install and lifecycle | Linux CI provisions and starts the service, verifies idempotent provisioning and unit enablement, then exercises MQTT request handling | CI does not simulate host reboot or power interruption |
| Native ARM64 pilot | CI matrix runs this same disposable pilot on a native ARM64 Linux runner; report architecture distinguishes it from amd64 | Cross-compilation or emulation is not native hardware acceptance |

The runner's observed checks are authoritative for a given invocation. This table
describes the intended coverage; consult the report's `checks` and `not_run` arrays
for what actually ran. On native `aarch64`/`arm64`, `native_arm64` is omitted from
`not_run`; on other architectures it remains explicitly unverified. The report records
the architecture, source SHA and dirty flag, legacy tag SHA, and tool versions.
