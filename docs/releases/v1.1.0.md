# Captain Compose 1.1.0

**Stable release:** 1.1.0 promotes the runtime tested as `v1.1.0-rc.2` at
`c9acf7f37e7749408115de8a2b2225e644641bcd`. The isolated fourth pilot
attempt completed on 2026-10-12 with 259,200 observed seconds, 9,001 successful
inspections, a maximum 31-second sample gap, 17 passed checks and no failures.
[The complete report](evidence/v1.1.0-72h-pilot.json) records its source SHA,
scenarios and exclusions; the [verification record](evidence/v1.1.0-72h-pilot-verification.json)
binds the report checksum to the exited container. Earlier interrupted or failed
attempts do not count.
The stable tag changes release documentation and version defaults; agent,
operator and pilot runtime code are unchanged from the observed candidate.

This release adds day-to-day operations to the MQTT deployment agent. Both the
`captain-compose` operator and `captain-compose-mqtt` agent ship in each platform
archive. Ubuntu 24.04 with systemd and Docker Compose 2.20+ remains the production
reference environment; Windows and macOS support development with Docker Desktop.

## Operator workflow

- Configure named environments and keep MQTT credentials in private files.
- Run `doctor`, preview `plan`, then `deploy` with an exact request file for retries.
- Use `status` and `inspect` for observed containers and safe revision history.
- Use `result` or `wait` when command delivery or completion is uncertain.
- Require the expected revision for `revert` and explicitly acknowledge that
  application data does not roll back with its Compose configuration.

Version 2 introduces revision guards, expiry before first execution, independent
result delivery, bounded query capacity, and queryable request receipts. Existing
version 1 commands remain supported. Delivery uses at-least-once MQTT; request
deduplication and saved results reduce repeats but do not make application side
effects exactly once.

## Operating a host

Optional loopback HTTP endpoints expose health, readiness, observed status and
Prometheus metrics. An optional MQTT status topic carries heartbeats. The installer
verifies checksums and GitHub provenance for the exact tag and release workflow;
offline attestation bundles accompany the archives. Ansible provides repeatable
installation with protected credentials and preflight checks.

Backup and staged restore cover agent state and configuration. Workload volumes
need their own application-aware backup. Restore preserves previous directories
and leaves the service stopped for verification. See the [lifecycle guide](../lifecycle.md)
and [credential rotation](../credential-rotation.md).

## Upgrade from 1.0

Stop the service and take a complete state/configuration backup before upgrading.
The 1.1 agent reads 1.0 journals and deployment manifests and writes versioned
deployment state. A binary-only downgrade is unsafe: restore the complete matching
1.0 backup before running 1.0 again. Keep application data backups separate.

Install the archive's scripts with an explicit release version:

```bash
bash scripts/install.sh --version 1.1.0 --prefix "$HOME/.local/bin"
captain-compose --version
captain-compose-mqtt --version
```

## Verification boundaries

CI includes operating-system race tests, native Linux ARM64 tests, real Docker/MQTT
integration, protocol/schema contract fixtures, Linux systemd and Ansible convergence,
archive safety and restore failure recovery, and an isolated upgrade/fault-injection
pilot. A two-minute pilot verifies its named scenarios, not multi-day stability.
The linked 72-hour run records its actual observation duration and results in JSON.
Physical reboot and power-loss recovery require suitable infrastructure and are not
claimed by the nested Docker pilot. Neither host systemd lifecycle nor native ARM64
was part of that run; separate CI covers Linux service behavior and ARM64. See the
[acceptance matrix](../acceptance-matrix.md).
